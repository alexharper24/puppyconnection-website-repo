# puppyconnection-website-repo

Concept build of **puppy-connection.com** for its new purpose: a paid listing
directory where breeders pay $14.99 per puppy, keep control of their own
listings, and buyers are handed straight to the breeder. Puppy Connection never
sells a puppy.

Client: Amber Blakeslee. The live site is Wix; a half-built Wix duplicate
("Puppy Connection Copy") holds her new marketplace design, which she built
herself with ChatGPT's help.

**Status: eight-page concept for review. Not a production site.**

**Live for review:** https://alexharper24.github.io/puppyconnection-website-repo/

Every page carries `noindex, nofollow`, `robots.txt` disallows all crawlers, and
a "concept build" banner sits above the header. The repo is public only because
GitHub Pages requires it on a free plan.

## Run it

```bash
python -m http.server 8161 --directory puppyconnection-website-repo
```

Or `preview_start` the `puppyconnection` entry in `.claude/launch.json` (port 8161).
It also opens straight from the filesystem: data is a plain `window.PC_*` global
in `data/data.js`, so there is no fetch and no CORS problem.

## Decisions this build encodes (Alex, 30 Aug 2026)

- **Price is shown.** Breeders manage their own pricing.
- **Primary action is the breeder's own contact details**, in priority order
  website, phone, email. No form, no cart, no deposit.
- **Litters are the unit with a lifecycle.** A placed puppy stays visible inside
  its litter and on its breeder's page. The open browse view leads with what is
  available; one toggle reveals the rest.
- **$14.99 appears on the breeder service page only.**
- **No buyer accounts.**
- Existing logo, palette and typefaces retained. See `BRAND.md`.

## Data

`data/data.js` is generated by `_harvest/builddata.py` from a full harvest of the
live catalog. Re-run it after changing anything under `_harvest/`.

| | |
|---|---|
| Listings | 204 |
| Images | 1,651 |
| Litters derived | 35, covering 155 puppies |
| Breeds | 24 |
| Breeder profiles | 12 |
| Status split | 174 available, 28 adopted, 2 pending |

**Litters are real, not invented.** They are derived from matching breeder
domain plus birthdate, which is genuinely how a litter presents in her data.

**Breeder identity comes from the listing's domain**, not a staged pairing, so
the name on a listing always agrees with the contact links beside it. The catalog
references exactly four breeder businesses: Peaceful Paws Puppies (103 listings),
Responsible Dog Breeder (46), Chain O' Lakes Companions (26) and Kingdom Family
Companions (6).

**Her twelve written breeder profiles are shown separately**, on `breeders.html`.
The live data does not link them to any listing, which is one of the joins worth
making. Profile pages carry a visible note saying so.

## Things found in her live data, worth raising

- **Status lives inside the product name.** 28 listings are prefixed `*ADOPTED*`
  and 2 `*PENDING ADOPTION*`. This build lifts that into a real `status` field
  and cleans the display name. It is the clearest possible argument for a proper
  status field.
- **Breed strings already fragment.** The catalog contains both
  `Miniature Poodle` and `Miniature  Poodle` (double space), plus
  `Cavalier King Charles` alongside `Cavalier King Charles Spaniel`.
  `builddata.py` normalises them through an alias map.
- **`responsibledogbreeder.com` is itself a listing directory**, not a single
  breeder, and it accounts for 46 listings. Its own pages carry logos for
  Family Affair Puppies, Winding Streams, Premier Bulldog, Cavaliers By Crumley
  and others. `chainolakescompanions.com` sits on a WordPress multisite path
  (`/uploads/sites/31/`) referencing `net.responsibledogbreeder.com`, so two of
  her four breeder sources are the same platform. Worth asking Amber whether she
  knows she is referring traffic to a competing directory.
- **21 of 204 listings carry no breeder contact of any kind.** The listing
  template degrades to "contact details are being confirmed" rather than
  breaking.
- The Add Puppy form's **Breed dropdown was never populated** and still holds
  Wix's `Item 1 / Item 2` placeholders, so the breed list here is derived from
  actual inventory instead.
- **Contact fields run together in the source.** Descriptions contain
  `...@chainolakescompanions.comWebsite: www...` with no separator, which
  corrupted 33 of 35 email addresses on a naive parse. Re-parsed to stop at the
  TLD.
- **Descriptions duplicate every structured field.** Each one repeats price,
  deposit, birthdate, ready date and parent weights before the prose starts,
  then repeats the includes list and contact block after it. The build cuts to
  where the narrative begins, which is reliably the puppy's own name.
- **Only 8 of 24 listed breeds have a guide page.** Havanese is her largest
  breed at 26 listings and has none. Breed pages are what search traffic lands
  on, so this is a real content gap. `breed.html` shows an explicit empty state
  rather than hiding it.
- **"Hereceives" appears in three descriptions** in her source data. Fixed here
  only because it is unambiguous.

## Known limits of the concept build

- **Images are hot-linked to the Wix CDN.** Fine for review, and it keeps the
  repo small. They must be localised before any production launch, per the
  root `CLAUDE.md` rule.
- The hero photograph sits under a different Wix media account than her own
  uploads, so it is probably stock. **Confirm licensing before production use.**
- DIN Neuzeit Grotesk is licensed through Wix and cannot be carried over.
  Barlow stands in for it here.
- `data/data.js` is 398 KB and ships the whole catalog to the browser. That is
  a demo shortcut; a real build queries a database.
- The header, nav and footer are duplicated across pages, per house convention
  for static builds. `_harvest/genpages.py` regenerates the seven inner pages
  from `index.html`, so change `index.html` first, then re-run it.

## Image handling

Measured on the browse page: 18 images, 680 KB total, 38 KB average, median
load 495ms. Before these changes a single card image was 242 KB.

- **Right size per slot.** 600px cards, 160px thumbnails, 900px breed photo,
  1000px gallery. Every context previously pulled the same 1400px rendition,
  which is what made the grid feel slow. That alone was 242 KB to 49 KB.
- **`enc_auto`** lets Wix negotiate AVIF or WebP. Another 45% off: 49 KB to
  27 KB on the same crop.
- **Every image slot is 3:2**, because that is what her photography is.
  Sampled 24 first-images: median aspect 1.50, 18 of 24 landscape, 5 portrait.
  At 3:2 the landscape majority crops by nothing at all.
- **Grids crop, detail views do not.** Cards use `fill` at 3:2. The main gallery
  image and the breed photo use `fit`/`contain`, so a portrait letterboxes
  against the warm frame rather than losing the dog. On the page where someone
  is choosing a puppy, a whole dog beats a full-bleed crop.
- Anchoring a crop to the top does **not** rescue portraits: on a tall photo the
  top is usually sky or fence, not the dog. That is why the detail views contain
  rather than crop.
- HTML `width`/`height` attributes act as presentational hints, and when both
  are definite CSS `aspect-ratio` is silently ignored. Images whose shape is
  set in CSS carry no size attributes.

### Where the images actually come from

Only these are in the repo:

| Path | What |
|---|---|
| `img/brand/` | Logo (white, charcoal, trimmed) and the home hero |
| `img/breeders/*.webp` | The four breeder logos, trimmed and converted, 140 KB total |

**Every puppy photo is hot-linked from the Wix CDN.** Nothing is stored locally
and nothing is a local WebP. Wix serves them as AVIF via `enc_auto`, at the size
each slot asks for, which is smaller than a self-hosted WebP would be.

**Would self-hosting be faster?** Marginally, and not for the reason it looks.
Wix's CDN is a real CDN and byte size dominates, which is now fixed. Hosting
them yourself saves one DNS lookup and TLS handshake to a second origin, worth
something on the first image and little after. Localise them for **durability**,
not speed: if the Wix subscription lapses, hot-linked images vanish. Doing it
properly means roughly 1,650 source images at three widths each, so it is a real
job and belongs in a production build rather than a concept.

## Interaction notes

- Results render 40 at a time with a "show more" control. Rendering all 200
  cards on every filter change was the source of the lag; filtering is now
  about 4ms.
- The filter rail scrolls independently, and hands scrolling back to the page
  once it reaches either end (no `overscroll-behavior: contain`).
- The listing detail column spaces its stacked blocks so the facts, the
  goes-home-with list and the breeder box read as separate.
- The description sits under the gallery in the left column, which balances the
  two columns to within about 10px instead of leaving the left one short.
- On phones the main menu is full height rather than a short dropdown with the
  page showing beneath it. It starts below the sticky header (whose height is
  measured into `--hdr-h`, since the logo and tagline make it variable), pins
  the "List with us" call to action to the bottom, locks body scroll, closes on
  Escape, and the button relabels itself Menu / Close.
- On phones the browse filters are a slide-in drawer behind a "Filters · N puppies"
  button, rather than a block occupying the top of the page. Backdrop, Escape,
  body scroll lock and focus handling included.
- On phones the listing page puts breed, name and price above the gallery. The
  page uses named grid areas so the title can reorder without moving the gallery.
- On phones the breed page hides its sidebar photo, which is redundant next to
  the listing grid below it.
- Breeder pages show the breeder's own logo above their contact details, and no
  longer carry an initial-letter square beside the name: two marks competing for
  the same identity read as clutter.
- Logo cards are white by default. Kingdom Family Companions' wordmark is white
  on transparent (mean luminance 249), so that card goes dark instead. Backdrop
  is chosen by measuring the mark, not by recolouring someone else's logo.

## Stacking contexts, twice

The mobile menu is a descendant of `.site-header`. A positioned descendant
paints above its ancestor's background no matter what z-index it carries, so
the full-height menu covered the logo and, worse, the button used to close it.
Raising the header did nothing; the fix is lifting the menu's *siblings*
(`.brand`, `.burger`) within the header's own stacking context.

## A bug worth remembering

The first version of the filter drawer froze every page under 940px: the whole
site appeared greyed out and nothing was clickable, including the main menu.

`.rail-backdrop{display:block}` sat inside the mobile media query. A class
selector beats the UA stylesheet's `[hidden]{display:none}`, so the full-screen
overlay at `z-index:79` was displayed permanently, sitting over the header and
swallowing every click. The JS was toggling `hidden` correctly and having no
effect at all.

Two lessons. Never set `display` on an element whose visibility is driven by
the `hidden` attribute; drive it from the same state class as everything else.
And assert with `document.elementFromPoint`, not `!el.hidden` — the original
test checked the JS property and passed while the page was unusable.

## Testing note

The in-app browser pane **never advances CSS transitions**: a `CSSTransition`
reports `playState: "running"` with `currentTime` frozen at 0, so
`getComputedStyle` returns the start value forever and even an inline
`!important` appears to be ignored. It cost several rounds on the filter drawer.
To assert a transitioned end state, inject `transition:none !important`, cancel
running animations, then measure. Or assert on the class, per the root
`CLAUDE.md` note.
